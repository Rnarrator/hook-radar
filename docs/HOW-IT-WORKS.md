# How the Auto Snapshot edition works

## The time rule, in plain words

The always-on Hook Radar server counts a price or volume figure only while it is **less than five minutes old at the moment you look**. A site made of plain files cannot do that: by the time you open it, the data is hours old.

So this edition moves the five-minute rule from the moment of viewing to the moment of collecting:

1. The collector first gathers **identity and discovery** slowly and politely: the hook registry, which pools exist, which hook a new pool uses.
2. Then it takes **all measurements in one burst**, a few minutes at most: the DEX Screener batches, a small GeckoTerminal fallback and, last, Frontier's own figures for the pools of its hooks (three requests). Almost all measurements in a snapshot (at least 90% of those priced) are therefore within five minutes of the snapshot's time.
3. The snapshot's time (`generatedAt`) is the moment the burst ended, Frontier's step included. Each pool keeps its **own** measurement time, worked out from the data service's reply headers exactly as the live server does it. Nothing is re-stamped with the current time.
4. The page treats "now" as the snapshot's time when it decides what counts. A measurement less than five minutes before the snapshot counts as current as of the snapshot. An older one is left out of totals, as live Hook Radar would leave it out. The five-minute limit itself is not changed.
5. Wherever the live page would say "2m ago", this edition shows an absolute time ("measured 14:03 UTC"). One line at the top states when the snapshot was taken and how old it is. That age is the only thing worked out from your own clock, and it is for display only. When the snapshot is more than four hours old by that clock, the line stops saying that the page is refreshed every few hours and says that the snapshot is old.

This is a deliberate, labelled difference from the live application. It is not "the same freshness, cheaper".

## 7D and 30D volume

The providers report 1-hour, 6-hour and 24-hour volume only, so 7D and 30D are a different kind of figure and are shown as one.

- **Complete days only.** A figure is the sum of a pool's USD volume over the last 7 (or 30) **complete UTC days**. The day still in progress is never counted, so a stored day never changes and a figure never mixes a part-day with whole days. The page says which day the figures run to ("Full UTC days through 11 Nov. Largest pools only.") and each pool's tooltip gives the time GeckoTerminal's answer was true. A figure therefore lags the live 24H figure by up to a day.
- **Largest pools only.** One request per pool is needed, so the collector reads only the largest pools by current 24-hour volume (up to 60, joining at rank 40). Every total (a project, a network, the Discover tile) is a sum over the pools that have a figure, marked "at least" (≥) and with "N of M pools covered" in its tooltip. A pool without one is a dash, never $0. A real $0 is a pool with daily volume that summed to nothing. A pool younger than the span says "since launch" and counts from its launch day. A compact total ("≥$2.31B") is rounded to the nearest unit the way every figure on the page is, so it can sit a few million above the true lower bound; the tooltip gives the exact figure ("At least $2,307,258,749.30"). That convention is the same on every page and is a known one to revisit everywhere at once (by rounding lower bounds down), not on one page.
- **Not the five-minute rule.** A completed day is not a measurement that ages, so the five-minute qualification does not apply to it. 1H, 6H and 24H keep it exactly. A 7D or 30D figure is dated by its end day instead, and is not shown once its end day is more than a day behind the snapshot's newest complete day.
- **Where it comes from.** GeckoTerminal's daily answer for each pool, read after the measurement burst (so it can delay nothing the page judges) and only twice a day per pool. The page asks for `data/daily.json` only when a visitor picks 7D or 30D, and shows the buttons only when the snapshot names the file as a source. The 24H figure can come from another provider (DEX Screener, Frontier), so a pool's 7D can look small beside its 24H.
- **Downloads.** With 7D or 30D chosen, the CSV carries that figure, blank where a row has none, and says "at least" in its column title. The JSON is the whole snapshot and does not include 7D or 30D figures; it only records which span the list was showing.
- **On the Analytics page.** Analytics offers the same switch, and the full analytics view behind "Explore pools & hooks" follows it. The page is drawn from the overview file for the chosen network, and every overview file carries a ledger of the measured pools (network, use case, project link and the 24H volume at the snapshot). 7D and 30D are the daily figures joined to that ledger in the browser, so the network and use-case bars, the two ribbons and the first tile are sums over the pools that have a figure, marked "at least", and their shares are shares of that covered total. No snapshot is downloaded for it, and `data/daily.json` is asked for only when a span is chosen. The scope line says how much of the tracked 24H volume the covered pools hold (both numbers say 24H); that is a fact about the covered pools, never an estimate of the rest. A pool the daily file lists but this snapshot has no current measurement for is left out and counted in the first tile's tooltip. Reserves, pools with trading, the recorded history and the evidence stay the snapshot's 24H measurements and say so. In the full view the ranked hooks and the pool table have a 7D or 30D column (sortable; a pool younger than the span says "since launch") and the CSV carries five more columns, `span_window`, `span_through`, `span_volume_usd`, `span_basis` (`exact` for a pool, `at_least` for a total) and `span_covered_pools`; without a span the CSV is as before. Pressing a span does not move the page. The ribbons and the summary line of the Data notes keep the height of the tallest span shown for that network and metric at that width (a span lists fewer networks and use cases, so its legend can wrap onto fewer lines), and the summary reads "As of the snapshot · 7D through 11 Nov" so that it is never longer than the 24H wording. Three things can still move. A block can grow on the first press when a span's own figures read wider than the 24H ones (a share of 2.9% against 4% can wrap one more legend line); it then keeps that height. At a few window widths, each about 15 px wide, the scope line's wording under a span is longer than its 24H wording and wraps one row earlier, which moves the tiles by one line. And the contributor bars further down are as long as the list of networks and use cases that have a covered pool, so that section can be shorter under a span. The tile's tooltip holds the exact total and the facts about the covered pools (how many are younger than the span, when the answers were read, which daily pools this snapshot cannot place); a phone has no tooltip, so the second paragraph of the Data notes says the same.
- **What else the Analytics span changed.** The 24H Analytics tile reads "Pools with trading · 24H" (it said "Pools with trading"), so that it does not change its label when a span is chosen. The caption row under the switch reserves its two lines on every page that has the switch, so on the narrowest phone (320 px) Discover, Networks and the Watchlist are 8 px taller than before; at 390 px and 1440 px they are the same. When the daily file is missing or not valid, pressing 7D or 30D removes the two buttons (as on Discover), so the switch gets narrower.
- The Analytics "History range" (24 hours, 7 days, 30 days, All) is a different thing: the recorded series of the tracked 24-hour volume. It is its own control, `analytics_range` in the address, and a span is `window=d7` or `window=d30`.

## What is sampled

The edition does not index every hook pool on every network. It follows a **sample**:

- `state/pools.json` holds the hooked pools the edition knows. It was started from the live application's public data and grows a little each run through discovery.
- Discovery looks at one page of each network's top pools by 24-hour volume on GeckoTerminal per run, rotating through the pages. A pool that is new to the edition is checked once against the v4.xyz indexer to learn which hook it uses. A pool with no hook is remembered in `state/hookless.json` and never looked up again.
- Measurement asks DEX Screener about the pools it chooses, in batches. Every run asks about the pools that answered in the last three days and the pools first seen in the last three days; the others are asked in turn, on a rotation of 3, 6 and 12 hours (pools that answered three to seven days ago, pools that answered longer ago, and pools that never answered), in at most 220 batches. When many pools are waiting for their turn the limit of 220 can leave some of them for the next turn, and the snapshot's DEX Screener note says so when it happens. A pool that was not due is not asked in that snapshot, so the page's "checked" counts are those of one snapshot, and a pool that was not asked is unchecked there, never zero. If DEX Screener does not answer for a larger network (one with 50 or more pools that answered recently), the run is refused and the site keeps its last snapshot, so a network is not left out of a figure without a word. If the plan misbehaves, the collector asks about every known pool instead: the repository variable `COLLECTOR_FULL_PLAN` set to `true` does it by hand, and the collector does it by itself, and says so in `status.json`, when the plan would ask about too few pools. Measurement keeps only rows that agree with the pool asked for: the same pool address, Uniswap, version 4, matching tokens. A pool the service does not return is shown as **unresolved**, never as zero. A batch that fails (a dropped connection, a timeout, a server error) is asked again once, at most eight a run (the repository variable `COLLECTOR_RETRY_MAX_BATCHES` can lower that, and `0` switches it off), and the snapshot's note says how many failed and how many recovered; a network DEX Screener does not index is not a failed batch and is not in that sentence. A small fallback (up to six requests) to GeckoTerminal can cover some of them: in every run it asks first about the pools it priced in the last three days that DEX Screener did not price in that run, as many as its first four requests reach (up to 120 pools, the networks with the most such pools first), and the rest of its requests go in rotation to the pools of every network, so each network is asked about from time to time, and a pool that GeckoTerminal priced is asked about again and stays in the snapshot while those requests reach it.
- A short **priority list** (`state/priority.json`, 1,355 pools) records the pools of the exact hooks that reviewed launchpad platforms publish as their own and of named projects' hooks, chosen once from the live application's last snapshot, plus the busiest pools of Doppler, Clanker, Zora and Flaunch. With the plan above it no longer chooses which pools a run asks about (a pool is asked when it answered recently, is new or is due in turn); the plan that asks about every known pool, which is the way back, still puts the list first. A pool on the list that DEX Screener does not return is still unresolved, never zero.
- **Frontier's pools are priced by Frontier.** After the burst the collector reads Frontier's own coin listing and ETH/USD statistics and queries the public AMM index Frontier's configuration names (the same reading the live application does, the same code). Frontier's rows are volume and core reserves of its Uniswap v4 pools, labelled as such; trades on a coin's bonding curve, before it graduates to a pool, are never counted. If Frontier or its index does not answer, the run goes on and the pools of Frontier's hooks keep what DEX Screener returned. When both measured a pool, the newer measurement stands, whole; the two are never combined.
- Projects come from the Uniswap hook registry. A project is credited with a pool only when registry evidence names that exact hook contract. A name, a website or a platform integration never earns ownership.

So the figures describe **the tracked hook pools**. They are not total Uniswap volume and not a market share.

## Quality gate

A snapshot is published only if it passes. The collector refuses, exits with an error and publishes nothing when:

- fewer than 500 hooked pools carry a current 24-hour volume (a volume of zero counts, a pool with only a liquidity figure does not),
- a provider rate-limited it, or the burst ran out of time, so that fewer than 80% of the pools the plan chose were requested,
- fewer than 80% of the pools that were requested were answered, so a provider that fails on and off cannot pass because its failures were not in a row,
- fewer than 90% of the pools that carry a measurement are current at the snapshot's time,
- fewer than 60% as many pools carry a current 24-hour volume as behind the previous snapshot's point, when that point is less than a day old (a sample that shrank to a fraction is not recorded as a fall in volume), or
- the data does not pass the same checks the page uses to read it.

When a run is refused the site simply keeps the previous snapshot. A green run can still have had one provider stop: a provider stopping fails a run only when it leaves too few pools behind (fewer than 80% of the planned pools requested, or fewer than 80% of the requested pools answered, as above), so a run can pass with a few GeckoTerminal pages missing. `data/status.json` says which providers answered and which did not (the page's Data & sources dialog, which listed them too, is switched off at the owner's choice; see [PROVIDER-TERMS.md](PROVIDER-TERMS.md)).

## Being polite to data services

The collector introduces itself with a truthful User-Agent naming the project and its repository. It keeps a fixed gap between requests to each provider (at least 12 seconds for GeckoTerminal, 5 for the v4.xyz indexer, 0.4 for DEX Screener, 1 for Frontier and for its public index; the 7D and 30D step adds up to about 125 GeckoTerminal requests a day at that same gap, the last thing a run does, so a refusal costs it only that step), honours `Retry-After`, and never hammers: after the first 429 that says how long to wait (a `Retry-After` in seconds or as a date, or Cloudflare's rate-limit page, taken as 30 seconds), a price or pool provider is waited for once (at most 90 seconds), asked once more and given a doubled gap, and **a second 429, a 429 that names no wait or any 403 stops the provider for the rest of the run**. A run makes fewer than 400 requests in total. The gaps can be raised by environment variables but never lowered. [PROVIDER-TERMS.md](PROVIDER-TERMS.md) says what each provider asks of you.

## What the site reads

Everything is a static file under `data/`:

| File                                                                      | What it is                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `data/snapshot.json`                                                      | The snapshot: measured pools, projects, coverage, which providers were used and how many requests each took                                                                                                                    |
| `data/overview-all-h1.json`, `-h6`, `-h24`, `overview-<network>-h24.json` | The Analytics overview for each time window and network, computed by the project's own analytics code from the same snapshot                                                                                                   |
| `data/daily.json`                                                         | 7D and 30D volume of the largest pools: for each, the sum of its last 7 and 30 complete UTC days and when the answer was true, at most about 10 KB. Optional: a snapshot names it as a source (`geckoterminal-daily`) exactly when it exists, and the page reads it only when a visitor picks 7D or 30D |
| `data/history.json`                                                       | One point per successful run: total tracked 24-hour volume and the number of pools behind it. At most 2,016 points, newest last (84 days at one run an hour, if no run is skipped; GitHub may delay or start no scheduled run) |
| `data/status.json`                                                        | When the run started, when the measurement burst started and ended, counts, sources and the collector version                                                                                                                  |

The page never asks a server anything. Anything that needs one is switched off.

| Figures expire five minutes after measurement, at your clock                                               | Figures are judged at the snapshot's time and shown with absolute UTC times                                                                                                                                                                         |
| 1H, 6H and 24H volume                                                                                      | The same, and 7D and 30D of the largest pools: complete UTC days, "at least" totals, dated by their end day                                                                                                                                         |
| Refreshes continuously                                                                                     | Refreshes about every hour, when GitHub starts the scheduled run, or when an external timer asks it for one                                                                                                                                         |

| Activity view and Refresh button                                                                           | Switched off, leaving no dead controls                                                                                                                                                                                                              |

## History and what is kept

`state/history.json` gains one point per successful run and is cut to the last 2,016 (84 days at one run an hour). A run that fails adds nothing. The history is real measurements only: a gap in the chart is a gap in the data, not something filled in.

## How a run starts, and what makes the hour dependable

Three things can start the Snapshot workflow: GitHub's own schedule (three lines in the workflow, at 7, 27 and 47 minutes past each hour, UTC), a person pressing **Run workflow**, and a call to GitHub's API from outside, which is what the optional external timer of [EXTERNAL-TRIGGER.md](EXTERNAL-TRIGGER.md) makes every 20 minutes. Whatever starts it, the workflow's first job, "Is a new snapshot due", decides. It reads when the last snapshot was saved. If that was under 45 minutes ago, the run ends green in seconds with "Nothing to do", publishing nothing and asking no data service anything. A run that failed under 90 minutes ago also holds the next one back.

GitHub's own schedule is **best effort**. GitHub's documentation says a scheduled run can be delayed when it is busy and that some can be dropped, and from 17:07 UTC on 11 November to 02:32 UTC on 12 November 2026 none was started (9 hours 25 minutes). So the hourly rhythm cannot be promised by that schedule alone. The external timer is what makes it dependable: it does not depend on GitHub's scheduler, so a call that gets no answer is followed by the next one 20 minutes later. It only asks. Its call sets the two boxes of **Run workflow**, "force" and "discover", to "false", which makes the gate treat it exactly like a scheduled run: the same 45 and 90 minutes and the same rule for the search for new pools. So it adds no request to any data service and does not make the site refresh faster than about an hour. Without the timer the site still refreshes when GitHub starts its scheduled runs.

## Where things happen

1. The Snapshot workflow starts (three times an hour by GitHub's schedule, every 20 minutes by the external timer if you have set it up, or by hand). Its first job, "Is a new snapshot due", ends the run at once, publishing nothing, unless a new snapshot is due; only a run that collects goes on to steps 2 to 5.
2. `node collector/run.mjs` collects, assembles, checks and writes `public/data/` and `state/`. If it exits with an error the workflow stops here.
3. `npm run build:static` builds the page into `dist/`, with the data files beside it.
4. `state/` is committed back to the repository.
5. GitHub Pages publishes `dist/`.

To look at it on your own computer: `npm ci`, `npm run build:static`, `npm run preview`. The folder as delivered has its first snapshot in `public/data`, kept out of Git by the folder's `.gitignore`, so a copy cloned from GitHub has none until a Snapshot run has produced one; it then needs the published address, or a collect (see the developer notes in [COLLECTOR-NOTES.md](COLLECTOR-NOTES.md)).
